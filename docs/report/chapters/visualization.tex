\section{Visualization}\label{sec:visualization}
Each view that follows answers a different question about the Citi Bike system.
This section presents them in turn, describing the encodings each one relies on, the interactions it supports, and the design decisions that produced it.

\subsection{Overview}
The application is structured as a multi-view dashboard, as introduced in Section~\ref{sec:introduction}. 
The global header hosts primary exploratory controls, while each view operates as a self-contained module with specialized visual representations.
We enriched the proposal with secondary plots that supplement these primary insights to offer broader analytical context.

To prioritize data legibility over decorative ornamentation, the design adopts a restrained aesthetic:
\begin{itemize}
    \item Neutral tones structure the interface, reserving vibrant color encodings strictly for semantic data attributes.
    \item Clean typography maximizes legibility, being consistent across all views and responsive to screen size.
    \item Minimal animation enriches the interface without distracting from the data.
\end{itemize}

\subsubsection{Implementation}
The frontend is a \emph{React} application built with \emph{Vite} and routed via \emph{React Router}. 
Layout and visual design tokens are managed through a unified \emph{Tailwind CSS} module, ensuring consistent styling across interface components, charts, and maps.

Each view employs a rendering library tailored to its specific data structures:
\begin{itemize}
    \item \emph{deck.gl} renders \emph{WebGL} map layers, maintaining interactive performance across thousands of stations and arcs.
    \item \emph{Plotly} generates three-dimensional surfaces and filled bands.
    \item \emph{Chart.js} and custom canvas routines handle two-dimensional categorical charts.
\end{itemize}

Although the original proposal specified \emph{D3.js} for non-map visualizations, adopting \emph{Plotly} and \emph{Chart.js} for standard visual controls freed development effort to focus on domain-specific encodings.

\subsubsection{User Experience}
To balance immediate legibility with analytical depth, the interface implements a three-part interaction model:
\begin{itemize}
    \item \textbf{Onboarding Guidance:} Each view features a collapsible ``How To Read It'' (Figure~\ref{fig:viz-guide}) panel with three practical interaction hints, lowering the entry cognitive load without restricting open-ended exploration.
    \item \textbf{Contextual Microcopy:} Embedded hints and hover-triggered tooltips surface exact values and fine-grained details on demand.
    \item \textbf{Progressive Disclosure:} Sensible default states offer immediate macro-level insights, while interactive filters, toggles, and linked selections enable deeper inspection.
\end{itemize}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{../media/report/guide.png}
    \caption{Example ``How To Read It'' panel}
    \label{fig:viz-guide}
\end{figure}

Regarding \textbf{page hierarchy}, the spatial map serves as the default view, offering an immediate and impactful geographic overview. 
Then, every view shares a standardized layout skeleton: a descriptive header, a primary display, secondary plots, and the collapsible reading guide.

\subsection{Header}
The global header incorporates two primary filter controls (Figure~\ref{fig:viz-filters}):
\begin{itemize}
    \item \textbf{Date Range Picker:} A calendar selector defining the temporal analysis window. Operating at a monthly granularity, it enforces a 12-month maximum range to prevent excessive backend query latency.
    \item \textbf{User and Bike Type Selectors:} A pair of selectors filtering data by membership status (member or casual) and bike type (classic, electric, or both).
\end{itemize}

Modifying any selection in the global header triggers a background data refetch to update the active plots, while preserving the filter state seamlessly across page transitions.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{../media/report/header.png}
    \caption{Header interface.}
    \label{fig:viz-filters}
\end{figure}

\paragraph{Challenges}
Managing global filter states introduced notable engineering trade-offs. 
Synchronizing parameters across views required a centralized state architecture. 
While this initially caused response latency challenges, backend optimizations successfully resolved them.

Beyond backend performance, this global constraint demanded resilient design. 
Each view was engineered to remain expressive under any valid filter combination, preventing sparse queries from yielding empty or misleading visualizations.

Centralizing the filters also narrowed the cross-filtering sketched in our proposal.
Under this updated architecture, view-specific filters operate independently and do not affect other views.

\subsection{Map}
To avoid visual clutter and cognitive overload, we separated the spatial analysis of Citi Bike usage into three focused map layers rather than combining them into one view.
As shown in Figure~\ref{fig:viz-overview}, users can easily navigate between these views using a basic selector.

\subsubsection{Station Usage}
This layer establishes where demand concentrates across the network, summarizing station activity into a form that remains legible at city scale.

\paragraph{Hexagon Heatmap}
Figure~\ref{fig:viz-station-usage} displays a three-dimensional heatmap of extruded hexagons, where height encodes absolute usage and color encodes a station's deviation from its mean activity.
This dual encoding provides an immediate, high-impact method to identify anomalies in both absolute and relative terms, especially in spatial perspectives.
In addition, the hexagonal binning approach aggregates stations, reducing visual clutter and enhancing the legibility of the spatial distribution of trips.

\paragraph{Map Controls}
Driven by precomputed hourly trip counts (Section~\ref{sec:data-pipeline}), the layer includes a mode selector to isolate incoming, outgoing, or all trips.
Temporal navigation is controlled via an interactive time wheel and play controls (equipped with speed and pause settings) to animate the daily average and reveal temporal usage patterns.
Map navigation is fully interactive, allowing users to pan and zoom across the city thanks to \texttt{deck.gl}.

    \caption{Station usage primary view: a 3D heatmap of station activity.}

\paragraph{Peak Hour and Station Rankings}
To complement the spatial view, two auxiliary plots provide targeted insights (Figure~\ref{fig:viz-secondary-station-usage}):
\begin{itemize}
\item \textbf{Station Usage by Peak Hour}: A bar chart showing the number of stations reaching peak volume at each hour. By abstracting fine-grained spatial details, it immediately highlights the network's peak stress hours.
\item \textbf{Busiest Stations}: A ranked bar chart of the top stations by average daily trip volume. This addresses spatial occlusion and crowding in the main map, making top-performing stations easy to identify individually.
\end{itemize}

\paragraph{Challenges}
Encoding thousands of stations and millions of rides on a single canvas created severe visual clutter and spatial occlusion, obscuring key usage patterns.
The design choices detailed above were specifically chosen to mitigate these visual artifacts.

Conversely, time granularity presented a lower-bound constraint, as the precomputed tables are aggregated by the hour.
To enable smooth temporal navigation, the time wheel interpolates linearly between adjacent hourly averages. 
This trade-off yields a continuous, fluid animation at the expense of rendering synthesized intermediate values rather than raw measurements.

\subsubsection{Trip Flow}\label{sec:viz-trip-flow}
While the previous layer quantifies activity at individual stations, this one examines the connections between them.

\paragraph{Corridor Arcs}
This layer renders origin-destination arcs representing trips between stations.
Arc width encodes trip volume, dynamically scaled against the busiest corridor in the current view.
Arc height and curvature carry no quantitative data, as they serve exclusively to disentangle overlapping paths and maintain visual readability across dense networks.
Stations are rendered as background points that recede behind the primary flow network until explicitly selected.
All flow metrics are derived from the precomputed station-pair aggregations (Section~\ref{sec:data-pipeline}) and normalized to daily ride averages to ensure comparability across varying observation periods.

\paragraph{Citywide Overview}
Initial loading presents a citywide overview of the primary transit corridors (Figure~\ref{fig:viz-trip-flow-overview}), providing an immediate macroscopic view of high-volume routes prior to user interaction.
To maximize visual reinforcement, a single-hue color ramp mirrors arc width, encoding volume across two perceptual channels.

\paragraph{Station Focus}
Selecting an individual station isolates its connected corridors and automatically re-frames the camera view around its dominant links (Figure~\ref{fig:viz-trip-flow-single-station}).
Upon selection, color semantics shift from absolute volume to directional flow asymmetry, categorizing linked stations as predominantly inbound, outbound, or balanced.
This state enables a directional filter to isolate one-way traffic flows, while re-selecting the origin station or executing a reset command restores the global overview.

\paragraph{Summary Cards and Corridor Ranking}
Two secondary analytical panels complement the spatial view (Figure~\ref{fig:viz-secondary-trip-flow}):
\begin{itemize}
    \item \textbf{Summary Cards}: Display high-level aggregates for the active context, including total daily rides, active corridor counts, flow-weighted median trip distance, and net directional shares for selected stations.
    \item \textbf{Ranked Corridor List}: A bar chart illustrating the top twelve corridors of the relative view. Interactive hovering highlights the corresponding spatial arc, while clicking a bar isolates that specific corridor by hiding all remaining network links.
\end{itemize}

\paragraph{Challenges}
Designing the origin-destination view required three major iterations.
The initial implementation rendered the entire network simultaneously, producing extreme visual clutter that obscured individual flows.
To resolve this, the second prototype hid all connections by default, revealing top corridors only upon station selection.
While this restored readability, it completely erased the macroscopic overview and discarded secondary routes.
The final design reconciles both perspectives by rebalancing visual encoding rather than truncating underlying data.

Additionally, visualizing directional flow introduced a distinct challenge, as geographic corridors carry no intrinsic orientation.
Because station pairs are stored in a canonical order, raw rendering would arbitrarily label flows as inbound or outbound based solely on database sorting.
To fix this, data rows are dynamically reoriented relative to the active station upon selection.
Furthermore, corridors are classified as directional only when traffic strongly favors one side. 
Otherwise, they are categorized as balanced to prevent minor fluctuations.

\subsubsection{Infrastructure}
Although bike-lane data was initially deferred in our project proposal, preliminary visual analysis revealed that infrastructure provides critical context for bike-share usage, leading us to promote it to a dedicated map layer.

\paragraph{Station Status and Bike Routes}
The default view renders station locations by real-time operational status (Figure~\ref{fig:viz-infrastructure}), highlighting stations that are nearly empty or full so users can assess capacity risks without inspecting individual nodes.
Additionally, an interactive toggle overlays NYC bike routes categorized by facility class (Figure~\ref{fig:viz-infrastructure-bike-routes}).

\paragraph{Station Sidebar}
Selecting a station opens a contextual sidebar merging real-time and historical metrics:
\begin{itemize}
    \item \textbf{Live Availability}: Reports effective capacity, open docks, and rentable bikes (disaggregated by classic and electric models), alongside out-of-service counts.
    \item \textbf{Historical Profile}: Displays hourly and daily ride distributions, identifying peak usage hours, busiest days, and overall arrival-departure balance.
    \item \textbf{Top Connected Stations}: Ranks the station's five strongest corridors. Selecting a corridor re-centers the interface on the partner station, allowing sequential exploration across connected routes.
\end{itemize}
In this way, we provide a comprehensive profile of each station without cluttering the map with excessive visual elements or auxiliary views.

\paragraph{Year Slider}
A temporal slider completes the infrastructure layer, allowing users to filter bike lanes by installation year.
By rendering only segments active in a selected year, the layer transforms from a static overview into a historical view of NYC's evolving cycling network.

\paragraph{Challenges}
Sentinel installation dates required careful handling rather than simple exclusion.
Segments marked with \texttt{01/01/1900} predate formal record-keeping, and dropping them would have omitted long-standing parkway paths from the network.
We retain these segments and clarify the convention in a chart note, ensuring the earliest temporal bin reads as a historical baseline rather than an active construction year.

Integrating real-time and historical datasets introduced an unavoidable temporal mismatch. 
While bike routes include installation and retirement timestamps, station metadata is available only as a live snapshot (Section~\ref{sec:data-pipeline}).
Consequently, the temporal slider filters the route network exclusively while holding station locations at their current state, avoiding speculative reconstruction of past station positions.

\subsection{Temporal}\label{sec:viz-temporal}
Setting geography aside, the temporal view isolates when the system is used, across both the hours of the day and the days of the week.

\paragraph{Surface Graph}
The temporal view centers on a 3D surface plot over a $7 \times 24$ grid of weekdays and hours.
A metric selector toggles the surface encoding between average ride volume, duration, distance, and speed.
Users can freely rotate the 3D surface to inspect temporal relief from any perspective, while hovering over individual points reveals exact values (Figure~\ref{fig:viz-temporal-surface}).

\paragraph{Comparison Mode}
Although global header filters can isolate specific user demographics or bike types, comparing them sequentially imposes a heavy cognitive load.
To address this, we introduced a multi-surface comparison mode (expanding upon our initial proposal) that overlays multiple surfaces within the same coordinate space (Figure~\ref{fig:viz-temporal-compare}).
Each surface maintains its own color gradient, with upper layers rendered semi-transparently to preserve the visibility of underlying topologies.

\paragraph{Histograms}
Two marginal histograms accompany the surface plot, aggregating data by weekday and hour (Figure~\ref{fig:viz-temporal-hist}).
To clarify cross-chart relationships, all three views are interactively linked: hovering over a surface cell highlights the corresponding bars in both histograms, while clicking a bar pins a specific day or hour.
Selecting a bar projects its distribution onto the opposite histogram and overlays a cross-sectional trace across the 3D surface.
In comparison mode, the histograms display colored bars for each active surface (Figure~\ref{fig:viz-temporal-hist-compare}).

\paragraph{Line Chart}
Because grid-level averages tend to mask single-day anomalies like holidays or severe weather, a supplementary line chart plots individual dates continuously.
This restores fine-grained detail and highlights temporal outliers that would otherwise remain hidden.

\paragraph{Challenges}
Comparison mode disables the multi-plot highlighting feature due to inconsistencies that arise when multiple surfaces are active.
Consequently, entering comparison mode clears active pins and limits slice selection.
This design intentionally separates two distinct tasks: deep-diving into a single population versus comparing high-level trends across multiple cohorts.

To prevent analytical ambiguities, comparison mode enforces three key structural safeguards:
\begin{itemize}
    \item \textbf{Duplicate Prevention:} Prohibits adding duplicate layers, as identical surfaces would only occlude each other without adding analytical value.
    \item \textbf{Filter Consistency:} Clears all pinned comparison layers whenever global header filters change, ensuring stale data is not compared against a newly selected population.
    \item \textbf{Canvas Persistence:} Prevents the removal or hiding of the final active surface so the visual canvas is never left empty.
\end{itemize}

\subsection{Weather}
This view proposes a compact summary of grouped weather conditions to provide detailed insights into daily bike usage patterns.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{../media/report/weather_scatterplot.png}
    \caption{Weather view: the condition scatter.}
    \label{fig:viz-weather-scatterplot}
\end{figure}

\paragraph{Condition Scatter}
The primary visualization is a scatter plot where each point represents a WMO weather code, positioned by average trip speed and rides per hour.
Each dot is color-coded by condition family (Figure~\ref{fig:viz-weather-scatterplot}), grouping into high-level categories (e.g., rain, snow, thunderstorm) simplifying interpretation.
This permits intuitive color semantics rather than raw numerical codes, allowing conditions with similar behavioral impacts to form distinct visual clusters. 
Then, interactive controls enable deeper data exploration.
Clicking a legend category isolates a specific condition family, while hovering over any data point surfaces a detailed tooltip with weather conditions and trip statistics.
This provides a compact summary of how weather suppresses or sustains global cycling activity, establishing baseline insights that supporting charts subsequently decompose.


\paragraph{Ridgeline Distributions}
Beyond reducing total volume, weather fundamentally alters daily usage patterns. 
To capture these temporal shifts, a ridgeline chart renders individual density curves per WMO weather code across either $24$ hours or $7$ weekdays, toggled via an interactive control (Figure~\ref{fig:viz-weather-ridgeline}). 
Each ridge is independently normalized to its peak, allowing low-frequency events (such as thunderstorms) to be directly compared against baseline conditions like clear skies..

\paragraph{Temperature and Rain Response}
Two supplementary plots complement the WMO condition categories by examining continuous weather variables directly (Figure~\ref{fig:viz-secondary-weather}):
\begin{itemize}
    \item \textbf{Temperature Response:} A line chart plotting average hourly rides across one-degree temperature bins, disaggregated by user type to contrast subscriber behavior against casual ridership.
    \item \textbf{Rain Impact:} A bar chart quantifying ridership loss across precipitation intensity tiers, expressed as a percentage of the dry-weather baseline.
\end{itemize}

\paragraph{Challenges}
Selecting appropriate axes for the scatter plot required several iterations to make anomalies both visible and explainable.
Initial attempts (such as plotting total rides against temperature) were dominated by common conditions like clear skies, collapsing rare events near the origin.
Conversely, pairing average duration with average distance yielded a highly correlated linear trend without meaningful clustering.
Normalizing volume to average hourly rides and pairing it with average trip speed resolved these issues.

Although our proposal designated the ridgeline chart as the primary visualization, it was less intuitive for first-time readers due to its height and emphasis on temporal shape over absolute rides magnitude.
We therefore promoted the scatter plot to the primary position and placed the ridgeline directly below it.
Then, normalizing each ridge independently required a deliberate trade-off: scaling each ridge to its own peak enables shape comparisons at the cost of absolute values.
Clear chart annotations and surrounding absolute-volume plots counteract this limitation, ensuring readers do not mistake relative temporal curves for absolute demand levels.

\subsection{Footprint}
The footprint view translates ridden distance into environmental impact using published emission factors and one adjustable assumption: the car-substitution rate.
A slider lets readers adjust this rate between 5\% and 25\%, updating the displayed visualizations.

\paragraph{Tiles and Emission Charts}
Three headline tiles summarize the selected distance ridden, avoided CO\textsubscript{2}, and car trips replaced (Figure~\ref{fig:viz-footprint}).
A horizontal bar chart compares the emissions that same distance would generate across different modes, including car, taxi, bus, subway, e-bike, and classic bike, isolating mode efficiency by keeping distance constant.
Finally, a cumulative chart plots daily avoided CO\textsubscript{2} over time, highlighting the impact of the car-substitution rate selection.
Shaded areas represent the range between the minimum and maximum substitution rates, while a dotted line tracks the current setting.
\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{../media/report/primary_footprint.png}
    \caption{Footprint view: the primary visualization.}
    \label{fig:viz-footprint}
\end{figure}

\paragraph{Pictogram}
Because absolute tonnage is hard to visualize, a pictogram translates the figures into familiar benchmarks: urban trees absorbing carbon annually, an average person's yearly emissions, and LED bulbs powered for a year (Figure~\ref{fig:viz-pictogram}).
To maintain readability, each row targets roughly 24 icons by rounding an individual icon's value to a clean multiple of 1, 2, or 5 times a power of ten.
Slider adjustments change the number of displayed icons without altering their unit value; conversely, adjusting the global date range updates the icon scale to keep the row length normalized.
\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{../media/report/secondary_footprint.png}
    \caption{Footprint view: pictogram visualization.}
    \label{fig:viz-pictogram}
\end{figure}

\paragraph{Challenges}
Unlike other views, this page displays modeled estimates rather than directly measured values.
To prevent users from mistaking avoided CO\textsubscript{2} figures for direct measurements, we prioritized explicit transparency.
An assumptions box outlines all baseline inputs, including modal emission factors, substitution rates from cited literature, and lifecycle exclusions (Figure~\ref{fig:viz-assumptions}). 
Inline citations provide direct links for verification.
