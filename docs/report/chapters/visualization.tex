Having processed and indexed the raw Citi Bike dataset into queryable API endpoints, the final step is visualization.

\subsection{Overview}
The application is structured as a multi-view dashboard, as introduced in Section~\ref{sec:introduction}. 
The global header integrates these views by hosting the primary exploratory controls, centralizing the user's ability to navigate and interact with the data. 
Each view operates as a self-contained module equipped with dedicated visual representations, control mechanisms, and explanatory guides, allowing users to focus on specific analytical tasks.

To preserve analytical clarity, the visual design employs a restrained palette:
\begin{itemize}
    \item Neutral tones are used for structural interface elements, reserving prominent color encoding strictly for semantic data attributes.
    \item Typography is selected for readability, omitting visual flourishes. 
    \item Animations and interface transitions are strictly not overwhelming, maintaining a professional environment tailored for deep visual analysis. 
\end{itemize}
This minimalist design directly reflects our proposal philosophy: prioritizing data legibility and depth over decorative ornamentation.

\subsubsection{Implementation}
The frontend is built as a \emph{React} single-page application using \emph{Vite} and routed with \emph{React Router}. 
Layout and visual design tokens are managed via \emph{Tailwind CSS}, where a unified token module defines all colors and typography. 
This ensures visual consistency across the interface components, charts, and map elements.

Each view leverages a specialized rendering library optimized for its specific data structures:
\begin{itemize}
    \item \emph{deck.gl} renders the map layers on a \emph{WebGL} canvas, maintaining interactive performance over thousands of stations and arcs.
    \item \emph{Plotly} generates three-dimensional surfaces and filled bands.
    \item \emph{Chart.js} and custom canvas routines handle two-dimensional categorical charts.
\end{itemize}

While our original proposal specified \emph{D3.js} for all non-map charts, adopting \emph{Plotly} and \emph{Chart.js} for standard visualizations and 3D controls freed us to focus on domain-specific encodings.

\subsubsection{Page Hierarchy}
The spatial map serves as the default view, offering an immediate geographic overview without overwhelming the user with initial complexity. 
To maintain consistency across the dashboard, every view shares the same layout skeleton: a descriptive header, a primary display, secondary plots, and a collapsible reading guide.
This structural choices minimizes cognitive load as they avoid a single, densely packed interface.

\subsection{Header}
The global header incorporates two primary filter controls (Figure~\ref{fig:viz-filters}):
\begin{itemize}
    \item \textbf{Date Range Picker:} A calendar selector defining the temporal analysis window. Operating at a monthly granularity, it enforces a 12-month maximum range to prevent excessive backend query latency.
    \item \textbf{User and Bike Type Selectors:} A pair of selectors filtering data by membership status (member or casual) and bike type (classic, electric, or both).
\end{itemize}

Modifying any selection in the global header triggers a background data refetch to update the active plots, while preserving the filter state seamlessly across route transitions.

\paragraph{Challenges}
Managing global filter states introduced notable engineering trade-offs. 
Synchronizing parameters across views required a centralized state architecture, though minimizing response latency initially proved challenging.

Our initial strategy relied on prefetching query data upon application load.
However, this approach created heavy memory footprints and network bottlenecks.
The precomputed summary tables of Section~\ref{sec:data-pipeline} removed the need for client-side prefetching altogether.

Beyond backend performance, this global constraint demanded resilient design. 
Each view was engineered to remain expressive under any valid filter combination, preventing sparse queries from yielding empty or misleading visualizations.

\subsection{Map}
To avoid visual clutter and cognitive overload, we separated the spatial analysis of Citi Bike usage into three focused map layers rather than combining them into one view.
As shown in Figure~\ref{fig:viz-overview}, users can easily navigate between these views using a basic selector.

\subsubsection{Station Usage}
Figure~\ref{fig:viz-station-usage} displays a three-dimensional heatmap of extruded hexagons, where height encodes absolute usage and color encodes a station's deviation from its mean activity.
This dual encoding provides an immediate, high-impact method to identify anomalies in both absolute and relative terms, especially in spatial perspectives.
In addition, the hexagonal binning approach aggregates stations, reducing visual clutter and enhancing the legibility of the spatial distribution of trips.

Driven by precomputed hourly trip counts (Section~\ref{sec:data-pipeline}), the layer includes a mode selector to isolate incoming, outgoing, or all trips.
Temporal navigation is controlled via an interactive time wheel and play controls (equipped with speed and pause settings) to animate the daily average and reveal temporal usage patterns.
Map navigation is fully interactive, allowing users to pan and zoom across the city thanks to \texttt{deck.gl}.

\paragraph{Challenges}
Encoding thousands of stations and millions of rides on a single canvas created severe visual clutter and spatial occlusion, obscuring key usage patterns.
The design choices detailed above were specifically chosen to mitigate these visual artifacts.

Conversely, time granularity presented a lower-bound constraint, as the precomputed tables are aggregated by the hour.
To enable smooth temporal navigation, the time wheel interpolates linearly between adjacent hourly averages. 
This trade-off yields a continuous, fluid animation at the expense of rendering synthesized intermediate values rather than raw measurements.

\subsubsection{Trip Flow}
This layer renders origin-destination arcs representing trips between stations, directly mitigating the straight-line bias discussed in \href{../../technical-report/technical-report.pdf}{\underline{technical report}}.
Arc width encodes trip volume, dynamically scaled against the busiest corridor in the current view.
Arc height and curvature carry no quantitative data, as they serve exclusively to disentangle overlapping paths and maintain visual readability across dense networks.
Stations are rendered as background points that recede behind the primary flow network until explicitly selected.
All flow metrics are derived from the precomputed station-pair aggregations (Section~\ref{sec:data-pipeline}) and normalized to daily ride averages to ensure comparability across varying observation periods.

Initial loading presents a citywide overview of the primary transit corridors (Figure~\ref{fig:viz-trip-flow-overview}), providing an immediate macroscopic view of high-volume routes prior to user interaction.
To maximize visual reinforcement, a single-hue color ramp mirrors arc width, encoding volume across two perceptual channels.

Selecting an individual station isolates its connected corridors and automatically re-frames the camera view around its dominant links (Figure~\ref{fig:viz-trip-flow-single-station}).
Upon selection, color semantics shift from absolute volume to directional flow asymmetry, categorizing linked stations as predominantly inbound, outbound, or balanced.
This state enables a directional filter to isolate one-way traffic flows, while re-selecting the origin station or executing a reset command restores the global overview.

\paragraph{Challenges}
A few dominant corridors crushed the rest into invisibility under a linear width scale.
We map volume to width with a square-root ramp and give the ranked corridors an opacity floor, so mid-tier flows stay legible while the busiest still stand out.
Consistency also required the live-versus-historical station join of Section~\ref{sec:data-pipeline}: arcs are drawn only between stations present in the live feed.



\subsubsection{Infrastructure}
This layer maps station dots colored by live status alongside bike routes colored by facility class.
It shows how the network is structured and how it grew.
Station status is fetched live, while route geometry is parsed in the backend from its stored text form (Section~\ref{sec:data-pipeline}).

Clicking a station opens a sidebar with live docks, recent history, and demand; a toggle shows or hides the routes; a year slider filters the network to a chosen year.
Alongside, diverging bars report the segments installed and removed each year, with borough and facility-class breakdowns.
Each segment is labeled by its best available facility class, a simplification inherited from the source data.

Our proposal deferred the NYC bike-lane data unless it proved necessary.
In development, the spatial view gained the most context from it, so we promoted infrastructure to a full layer.

\paragraph{Challenge: reconstructing the network's history.}
Segments carry an install date and, where present, a retirement date.
We use these to filter the routes by year and to compute the per-year additions and removals shown in the bars, turning a static map into a timeline of the city's cycling infrastructure.

\subsection{Temporal}
The temporal view centers on a three-dimensional surface over the $7 \times 24$ grid of weekday and hour, flanked by two marginal histograms, one by day and one by hour, and a line chart over the selected date range.
A metric selector switches what the surface encodes: ride count, average duration, distance, or speed.
The week has two periodic axes, so a surface shows their joint pattern, such as weekday commute ridges, that separate small multiples would fragment.
The histograms give the exact marginal for each axis, and the line chart shows the trend over calendar time.

The view reads from the hourly aggregates rolled up to day-hour cells (Section~\ref{sec:data-pipeline}).
The time spine matters here: zero-activity hours are retained, so averages are not inflated by silently dropping quiet periods.
Hovering a cell highlights the matching bars in both histograms, and clicking a bar pins that day or hour and overlays its profile on the other chart.
A compare mode stacks several user and bike combinations as separate surfaces.
This view stayed close to the proposal, which already sketched a surface paired with aligned charts.

\paragraph{Challenge: keeping three linked charts consistent.}
The surface, the two histograms, and any pinned slice must always agree.
We hold the hovered cell and the pinned day or hour in shared state, so a hover lights the correct bars while a pinned slice draws both on the opposite histogram and as a guide line on the surface.
This lets the user confirm a peak seen on the surface against its exact marginal value.

\subsection{Weather}
The weather view combines four charts that together answer whether, when, and for whom weather changes behavior.
A scatter plot places each weather condition by typical speed and trip frequency, colored by condition.
A ridgeline chart traces the rides-per-hour distribution under each condition, toggling between hour of day and weekday.
A temperature-response line chart draws one curve per user type across temperature bins.
A rain-impact bar chart compares ridership at each rain intensity to the dry-weather baseline.

All four read from trips joined to hourly weather on a complete grid (Section~\ref{sec:data-pipeline}); each trip is attributed the weather observed in its start hour.
Hovering a scatter point reveals its exact conditions, the ridgeline switches its axis on demand, and the global filters recolor the temperature curves to contrast members and casual riders.
Tight scatter clusters signal stable behavior, while a gap between clusters signals habits that shift sharply when conditions change.

\paragraph{Challenge: making rare conditions comparable.}
A heavy storm produces few hours, so its distribution is sparse and easily misread.
The weather grid fills missing cells with zero (Section~\ref{sec:data-pipeline}), and each ridge is normalized to its own peak, so a rare storm and a common clear hour become visually comparable rather than dwarfed.

\subsection{Footprint}
The footprint view translates ridden kilometers into environmental terms.
Three headline tiles report distance ridden, avoided CO\textsubscript{2}, and car trips replaced.
A horizontal bar chart re-expresses the same distance as emissions per transport mode, a cumulative band shows avoided CO\textsubscript{2} over time, and a pictogram renders everyday equivalents.
A slider sets the car-substitution rate.

The view reads from the precomputed daily distance and ride totals (Section~\ref{sec:data-pipeline}); the environmental figures are simple arithmetic on top, recomputed live as the slider moves.
Every factor is stated on the page: standard per-mode emission rates, an uncertain car-substitution rate, and explicit exclusions such as manufacturing and rebalancing.
Moving the slider shifts a dotted line inside the shaded band, and the equivalent icons rescale with it and with the selected date range.

\paragraph{Challenge: honesty about uncertainty.}
The proposal described a single figure for CO\textsubscript{2} saved.
A point estimate would overstate a number that rests on an unknown, namely how many rides truly replace a car trip.
We therefore present avoided CO\textsubscript{2} as a range bounded by low and high substitution rates, with the chosen rate marked inside it and every assumption listed openly.
The design challenge was to make this uncertainty visible without burying the headline message.

\subsection{Reading Guides and User Experience}
Every view carries a collapsible ``How To Read It'' guide: a one-line summary of the plot and two or three concrete hints.
The tool is exploratory and general-purpose, aimed at operators, city planners, and curious citizens alike.
The guide lowers the entry cost for a first-time reader without forcing a narrative, preserving the exploratory intent stated in the proposal.

Smaller cues serve the same goal.
Tooltips reveal exact values on hover, help icons explain each filter, and a hint appears whenever a control is disabled, so the interface never blocks the user silently.
Default views are chosen to give an immediate reading, while the filters, toggles, and linked selections reward deeper inspection.
This dual level, immediate insight over optional depth, is the interaction model we set out to build.
