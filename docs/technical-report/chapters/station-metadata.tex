\section{Station Metadata Dataset (GBFS)}
To enhance the station data provided by Citi Bike, we incorporate the real-time feed published in \href{https://gbfs.org/}{General Bikeshare Feed Specification} (GBFS) format and documented on the \href{https://citibikenyc.com/system-data}{Citi Bike System Data} page.

\subsection{Dataset Structure}
Unlike historical trip records, station metadata is served via a public JSON API adhering to MobilityData's \href{https://gbfs.org/}{GBFS} standard.
From this service, we query two key Citi Bike endpoints:
\begin{itemize}
    \item \texttt{station\_information.json}: Static properties like location and capacity, whose content changes only when the network itself changes.
    \item \texttt{station\_status.json}: Live availability and operational state.
\end{itemize}

\subsubsection{Original Structure}
The two endpoints share the numeric \texttt{station\_id} field, on which they are merged to produce a unified station record comprising:

\begin{itemize}
    \item \textbf{From \texttt{station\_information}:}
    \begin{itemize}
        \item \textbf{Station ID}: numeric GBFS identifier.
        \item \textbf{Short Name}: public station identifier used for joins with Citi Bike trip data.
        \item \textbf{Name}: station name.
        \item \textbf{Latitude} and \textbf{Longitude}: station coordinates.
        \item \textbf{Capacity}: number of available docks.
    \end{itemize}

    \item \textbf{From \texttt{station\_status}:}
    \begin{itemize}
        \item \textbf{Bikes available}: currently rentable bikes.
        \item \textbf{Vehicle types available}: per-type counts of the bikes currently at the station.
        \item \textbf{Docks available}: currently available docks.
        \item \textbf{Operational flags}: \texttt{is\_installed}, \texttt{is\_renting}, and \texttt{is\_returning}.
    \end{itemize}
\end{itemize}

Using the three operational flags (\texttt{is\_installed}, \texttt{is\_renting}, and \texttt{is\_returning}), we derive a boolean \texttt{active} indicator to filter out unavailable stations from live views.

The main quality issues concern station status, the interpretation of zero capacity, and identifier consistency.

\paragraph{Inactive Stations}
The feed is a registry of known stations rather than a list of working ones, so entries remain while a station is being installed, is temporarily out of service, or is being removed.
Such stations are present in the feed but not fully operational because one or more status flags are false, and they are excluded from live visualizations using the derived \texttt{active} feature.
The three flags are almost never in disagreement, as virtually no station allows rentals while refusing returns, which is what justifies collapsing them into a single indicator instead of modelling each flag separately.
These stations still hold a small but non-negligible share of the network's docks, so they must be excluded before computing capacity statistics, although they hold no rentable bikes and therefore cannot distort availability figures, the bikes left at them being all flagged out of service.

\paragraph{Zero Capacity}
A subset of stations reports a capacity of zero, which produces the isolated bar in Figure~\ref{fig:station_capacity}.
These are not missing values: they are stations that are not installed, and they consistently report no docks and no bikes.
Interpreting that zero as a real station size would understate the average capacity of the network, so these records are filtered through the \texttt{active} feature rather than through a capacity threshold.

\paragraph{Feed Self-Consistency}
The feed publishes the same quantities in more than one way, which allows checking it against itself.
Two identities should hold at every station: the docks must add up, so that available bikes, free docks and out-of-service bikes and docks together match the station's capacity, and the per-type bike counts must add up to the reported bike total.
Neither holds everywhere.
Figure~\ref{fig:station_consistency} shows the distribution of the dock reconciliation gap: two thirds of the stations reconcile exactly and the vast majority fall within a couple of docks, but a tail remains in which a large portion of the capacity is reported by no counter at all.
This is the same shortfall visible in Figure~\ref{fig:station_availability}, and it implies that any quantity derived from capacity should be treated as approximate.
The bike-type identity fails at only a handful of stations, but it affects the features we derive: where the dedicated electric-bike field and the vehicle-type list disagree, it is the vehicle-type entry that fails to reconcile with the reported total, which makes the derived split marginally less reliable than the field published directly.

\paragraph{Identifier Consistency}
Cross-dataset joins require attention because GBFS provides both a numeric \texttt{station\_id} and a public \texttt{short\_name}. Historical trip data use \texttt{short\_name}, therefore all joins are performed using this field after validating its consistency.

\paragraph{Missing Values and Cleaning}
The fields consumed by the pipeline are fully populated in the feed, so no imputation is required, and the notebook reports the missing counts at every run.
Consequently no cleaning is applied to station metadata: ingestion keeps every station returned by the feed and only casts types, the loader persists the identifier, name and coordinates while discarding duplicates on conflict, and inactive stations are filtered by the backend at request time instead of being removed from storage.

Additional issues, such as temporary feed outages or duplicate identifiers caused by station changes, are handled through preprocessing checks to maintain reliable visualizations.
