\section{Station Metadata Dataset (GBFS)}
To enhance the station data provided by Citi Bike, we incorporate the real-time feed published in \href{https://gbfs.org/}{General Bikeshare Feed Specification} (GBFS) format and documented on the \href{https://citibikenyc.com/system-data}{Citi Bike System Data} page.

\subsection{Dataset Structure}
Unlike historical trip records, station metadata is served via a public JSON API adhering to MobilityData's \href{https://gbfs.org/}{GBFS} standard.
From this service, we query two key Citi Bike endpoints:
\begin{itemize}
    \item \texttt{station\_information.json}: Static properties like location and capacity, whose content changes only when the network itself changes.
    \item \texttt{station\_status.json}: Live availability and operational state, which the specification classifies as near-realtime and requires to be no more than five minutes out of date.
\end{itemize}

\subsubsection{Original Structure}
The two endpoints share the numeric \texttt{station\_id} field, on which they are merged to produce a unified station record comprising:

\begin{itemize}
    \item \textbf{From \texttt{station\_information} (static):}
    \begin{itemize}
        \item \textbf{Station ID}: numeric GBFS identifier.
        \item \textbf{Short Name}: public station identifier used for joins with Citi Bike trip data.
        \item \textbf{Name}: station name.
        \item \textbf{Latitude} and \textbf{Longitude}: station coordinates.
        \item \textbf{Capacity}: number of available docks.
    \end{itemize}

    \item \textbf{From \texttt{station\_status} (live):}
    \begin{itemize}
        \item \textbf{Bikes available}: currently rentable bikes.
        \item \textbf{Vehicle types available}: per-type counts of the bikes currently at the station.
        \item \textbf{Docks available}: currently available docks.
        \item \textbf{Operational flags}: \texttt{is\_installed}, \texttt{is\_renting}, and \texttt{is\_returning}.
    \end{itemize}
\end{itemize}

\subsubsection{Extracted Features} %#TODO: Not sure if those can be considered extracted features or more like a cleaning step
Using the three operational flags (\texttt{is\_installed}, \texttt{is\_renting}, and \texttt{is\_returning}), we derive a boolean \texttt{active} indicator to filter out unavailable stations from live views.

The feed reports availability as a list of \texttt{(vehicle\_type\_id, count)} pairs, where a type may be missing.
We index it by type to derive \texttt{num\_classic\_bikes\_available} and \texttt{num\_ebikes\_available}, counting absent types as zero.

The main quality issues concern station status, missing attributes, and identifier consistency.

Some stations are present in the feed but not fully operational because one or more status flags are false. These stations are excluded from live visualizations using the derived \texttt{active} feature.

A small number of records may have missing capacity or coordinates. Stations without coordinates cannot be displayed on maps, while missing capacity only affects analyses based on station size.

Cross-dataset joins require attention because GBFS provides both a numeric \texttt{station\_id} and a public \texttt{short\_name}. Historical trip data use \texttt{short\_name}, therefore all joins are performed using this field after validating its consistency.

Additional issues, such as temporary feed outages or duplicate identifiers caused by station changes, are handled through preprocessing checks to maintain reliable visualizations.
